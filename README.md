# XSFC

**XSFC** — прошивка полётного контроллера на C++ для семейства ESP32.
Проект объединяет обработку IMU, контуры стабилизации, моторный микшер,
радиоуправление, телеметрию, Blackbox и навигационные подсистемы.
Конфигурация доступна через MSP и текстовый CLI; сборка — через PlatformIO.

Развитие проекта: [XScythelin](https://github.com/XScythelin).
XSFC использует сторонние компоненты и код из экосистемы полётных прошивок;
уведомления об исходных авторах и лицензиях сохраняются.

## Архитектура

Общее состояние и настройки разделены между `ModelConfig` и `ModelState`.
`Hardware` инициализирует шины и обнаруживает устройства, а менеджеры
подсистем связывают драйверы, обработку данных и контуры управления.

Упрощённый поток обработки:

```text
                       радиоприёмник
                             │
                             ▼
IMU → чтение → фильтры → Controller / PID → Mixer → ESC / servo
                  │              ▲           │
                  ▼              │           └─ DShot telemetry
                Fusion ──────────┤
                  ▲              │
        baro / GPS / range / flow ┘

MSP / CLI ↔ ModelConfig / ModelState → диагностика / Blackbox
```

### Выполнение и планирование

- Базовый цикл привязан к таймеру опроса гироскопа. На ESP32-P4 используется
  GPTimer; платформенные различия вынесены в target-слой.
- В многоядерной конфигурации чтение датчиков и обслуживание входов отделены
  от обработки событий gyro/accel, PID, микшера и Blackbox через очередь событий.
- Для одноядерной конфигурации предусмотрен последовательный путь выполнения.
- Контуры gyro, PID, mixer, accel и вспомогательные задачи имеют отдельные
  частоты, согласованные через таймеры и делители.
- `Utils::Stats` собирает длительность, частоту вызовов и нагрузку подсистем.

### Частоты: четыре разных величины

| Параметр | Значение |
| --- | --- |
| Частота шины | I2C SCL или SPI SCK; определяет время передачи |
| ODR | Частота обновления данных внутри датчика |
| Частота опроса | Как часто прошивка читает регистры датчика |
| Частота PID / mixer | Как часто рассчитываются управление и выходы |

Повышение скорости SPI само по себе не меняет ODR. Таймерный опрос регистров
не гарантирует чтение каждого образца: синхронизация DRDY/FIFO остаётся
отдельным направлением развития. Время синхронного ожидания шины входит
в измеряемую длительность операции и влияет на показатель нагрузки.

## Подсистемы

### Стабилизация и фильтрация

- Обработка gyro/accel и оценка ориентации в подсистеме Fusion.
- PID-контуры, настройка rates, масштабирование управляющих входов.
- Программные low-pass/notch-фильтры, конфигурация dynamic notch и RPM-фильтров.

На ESP32-P4 dynamic notch (`DYNAMIC_FILTER` во вкладке «Конфигурация»)
включён в заводскую маску features. Перепрошивка не заменяет сохранённые
настройки: для существующей конфигурации включите переключатель и сохраните
или выполните в CLI `set feature_dyn_notch 1`, затем `save`.
Для работы фильтра необходима частота PID loop не ниже 1000 Гц; при меньшей
частоте firmware исключает feature при проверке конфигурации. Значения
частот, Q и числа notch при включении переключателя не заменяются.
- Аппаратная фильтрация IMU настраивается драйвером и зависит от модели датчика;
  одинаковое имя настройки не гарантирует одинаковую полосу на разных IMU.
- Микшер преобразует управляющие воздействия в моторные/сервовыходы,
  учитывает лимиты и состояние arming.

### Радиоуправление и режимы

В дереве драйверов присутствуют **CRSF, SBUS, iBUS и PPM**. ESP-NOW зависит
от платформы и не используется текущим P4 target. AUX-условия задают режимы
работы; назначение UART и протокола приёмника конфигурируется отдельно.
Обработка входов включает состояние потери связи и failsafe.

### Выходы ESC и сервоприводов

- Протоколы PWM, OneShot, Multishot, brushed и DShot150/300/600 — в зависимости
  от target и конфигурации драйвера.
- На ESP32 используется RMT-путь генерации импульсов.
- Предусмотрена bidirectional DShot-телеметрия и обработка eRPM. На текущем
  P4 пользовательская проверка выявила 100% ошибок телеметрии на четырёх
  выходах при работающих моторах, затем interrupt WDT в legacy RMT ISR.
  P4 теперь использует собственный TX-done ISR и чтение RX-памяти без legacy
  ISR/FreeRTOS ring buffer; исправление ещё требует аппаратного подтверждения.
- Режим BEEPER может отправлять стандартную DShot-команду BEEP1 на ESC.
  Текущая реализация разрешает beacon только при disarm и остановленных
  моторных выходах; интервал команд — 500 мс.
- Внешний GPIO-зуммер — отдельная подсистема, не требуемая для ESC beacon.

### Навигационные компоненты

В проекте есть обработка GPS, барометрической высоты, дальномера и optical flow,
а также компоненты удержания высоты и горизонтального положения.
Эти возможности имеют собственные требования к качеству/свежести измерений
и не означают полной функциональной совместимости с INAV.
Алгоритмы, интерфейсы и текущие ограничения описаны в профильных документах.

### Blackbox и телеметрия

Blackbox использует компоненты Betaflight и поддерживает журналирование
полётных данных. Flash backend работает с выделенным разделом памяти;
параметры записи и доступные транспорты определяются конфигурацией.
Телеметрия обслуживается отдельно от формирования моторных выходов.

## Датчики и интерфейсы

### IMU

В исходниках присутствуют драйверы семейств MPU6050/MPU6500/MPU9250,
ICM20602, ICM20948, ICM42688, BMI160 и LSM6DSO. Доступность конкретной
комбинации интерфейса и модели определяется реализацией драйвера.

Особенности текущих ICM-драйверов:

| Датчик | Интерфейсы | Реализованные особенности |
| --- | --- | --- |
| ICM20948 | I2C / SPI | Проверка reset и конфигурации, banked registers, полный образец при чтении, DLPF/bypass |
| ICM42688-P | I2C / SPI | I2C 0x68/0x69, ODR 8 кГц, проверка полноты чтений; `gyro_dlpf` пока не управляет аппаратными фильтрами |

Для ICM20948 `gyro_dlpf = AUTO` выбирает включённый аппаратный DLPF;
`256Hz` и `EXPERIMENTAL` — bypass. Внутренний магнитометр AK09916 этого
датчика пока не реализован. Подробности: [ICM20948](docs/ICM20948.md)
и [ICM42688-P](docs/ICM42688.md).

### Остальная периферия

В дереве проекта представлены барометры BMP085/BMP280, MS5611, SPL06,
магнитометры HMC5883L, QMC5883L/QMC5883P, AK8963 и дальномер VL53L0X.
GPS и другие serial-устройства используют настроенные UART.
Присутствие драйвера не является матрицей аппаратной валидации всех плат.

### Обнаружение устройств

`AUTO` перебирает поддерживаемые модели; явно выбранная модель gyro ограничивает
поиск соответствующим драйвером. Для I2C перед первым регистровым обращением
проверяется ACK адреса, успешные адреса кэшируются. Ошибки последующих рабочих
транзакций не подавляются. Восстановление зависшей I2C-шины выполняется только
при запуске и имеет ограниченное число импульсов/ожиданий.

## Конфигурация и диагностика

### MSP и конфигуратор

XSFC реализует MSP и используется с **Betaflight Configurator Desktop 10.10.0**.
Это совместимость интерфейса настройки, а не реализация всех функций Betaflight.
Не все поля и возможности конфигуратора имеют соответствующую реализацию XSFC.

### CLI

CLI доступен через MSP-порт; символ `#` включает текстовый режим.
Основные команды:

| Команда | Назначение |
| --- | --- |
| `help` | Список команд |
| `get gyro` | Параметры gyro и программных фильтров |
| `get pin_output` | Назначения моторных выходов |
| `get pin_serial` | Назначения UART GPIO |
| `get pin_i2c` / `get pin_spi` | Назначения шин |
| `set <параметр> = <значение>` | Изменение конфигурации |
| `dump` | Выгрузка конфигурации |
| `devinfo` | Платформа, память и доступная диагностика IMU |
| `escinfo` | Пины ESC, состояние включения телеметрии и ошибки инициализации; без постоянного сбора отладочных данных |
| `stats` | Заданные частоты и фактическая статистика подсистем |
| `logs` | Журнал инициализации и обнаружения устройств |
| `save` | Сохранение и перезапуск |
| `exit` / `reboot` | Перезапуск без явного сохранения |

Пример выбора ICM42688 по I2C:

```text
set gyro_bus = I2C
set gyro_dev = ICM42688
save
```

Используйте полные имена перечислений: например, `188Hz`, не `188`.
Число CLI может интерпретировать как индекс, а не частоту.

Сохранённые значения имеют приоритет над defaults новой прошивки.
Изменения конфигурации требуют сохранения/перезапуска для согласованного
применения. Для текущего USB-пути P4 после `save` используется ручной
Disconnect/Connect.

## Платформы и платы

| PlatformIO environment | Базовая плата | Платформа сборки |
| --- | --- | --- |
| `esp32` | `lolin32` | `platformio/espressif32@6.12.0`, Arduino 2.0.17 / IDF 4.4.7 |
| `esp32s3` | `lolin_s3_mini` | `platformio/espressif32@6.12.0`, Arduino 2.0.17 / IDF 4.4.7 |
| `esp32p4` | FireBeetle 2 ESP32-P4 V1.0; build profile EV Board | Закреплённый pioarduino 55.03.31 |

Профиль платы PlatformIO задаёт параметры сборки; разводка XSFC задаётся
отдельно в `lib/Xsfc/src/Target/Target*.h`. Не следует переносить назначения
GPIO между разными платами только по совпадению семейства процессора.

### ESP32-P4 / DFRobot DFR1172

Текущий P4 target рассчитан на FireBeetle 2 ESP32-P4 V1.0:

- HP CPU 360 МГц, flash 16 МиБ, PSRAM 32 МиБ.
- USB Serial/JTAG для MSP; аппаратные I2C, SPI и пять HP UART.
- LP-core, SD, микрофон, C6 radio, камера и дисплей не инициализируются.
- Предел опроса gyro: SPI 4 кГц, I2C 2 кГц; фактическая частота зависит от ODR.
- I2C ограничен 400 кГц даже при большем сохранённом значении.
- Наличие PSRAM и фактические размеры памяти отображаются через `devinfo`;
  статическая RAM-оценка сборщика не описывает весь PSRAM heap.

Назначения по умолчанию:

| Назначение | GPIO |
| --- | --- |
| ESC M1 / M2 / M3 / M4 | 33 / 49 / 50 / 52 |
| UART0 TX / RX — MSP | 37 / 38 |
| UART1 TX / RX — MSP | 4 / 5 |
| UART2 TX / RX — Serial RX | 22 / 23 |
| UART3 / UART4 | Пины не назначены |
| I2C SDA / SCL | 7 / 8 |
| SPI SCK / MOSI / MISO | 28 / 30 / 29 |
| SPI CS gyro / CS барометра | 32 / не назначен |

Номера в таблице — GPIO. Полная разводка и миграция старых настроек:
[ESP32-P4-PINS.md](docs/ESP32-P4-PINS.md).

### Flash layout

| Target | Таблица разделов | Схема |
| --- | --- | --- |
| ESP32 / ESP32-S3 | `partitions_4M_nota.csv` | 4 МиБ, без OTA |
| ESP32-P4 | `partitions_16M_nota.csv` | 16 МиБ, один app slot, без OTA |

Для P4 приложению выделено 4 МиБ, данным/Blackbox — 11.875 МиБ,
coredump — 64 КиБ; NVS и служебные разделы сохраняют прежние адреса.
При смене разметки необходимо загрузить таблицу разделов вместе с приложением.
Старые Blackbox-логи из перемещённого раздела предварительно экспортируются,
а новый раздел очищается перед использованием.

## Сборка и загрузка

Требуются Git, Python и PlatformIO Core либо расширение PlatformIO для VS Code.
Зависимости и версии платформ задаются в `platformio.ini`.

```sh
git clone https://github.com/XScythelin/XSFC.git
cd XSFC
pio run -e esp32p4
```

Сборка другого target:

```sh
pio run -e esp32
pio run -e esp32s3
```

В текущей конфигурации environment по умолчанию — `esp32p4`.
Последние изменения проверялись сборкой P4; наличие остальных environments
не означает повторную проверку каждой комбинации после каждого изменения.

Загрузка и serial monitor:

```sh
pio run -e esp32p4 -t upload
pio device monitor -b 115200
```

Для явного выбора порта добавьте `--upload-port COM26` (под Windows)
или подходящее имя устройства вашей ОС. Порт monitor задаётся через `-p`.

### Артефакты

```text
.pio/build/<environment>/firmware.elf       ELF для анализа и символов
.pio/build/<environment>/firmware.bin       приложение
.pio/build/<environment>/firmware_0x00.bin  объединённый образ
```

Объединённый образ записывается по адресу **0x0** и включает загрузочные
компоненты/таблицу разделов. `firmware.bin` не является его заменой при
первичной загрузке или смене partition layout.

## Тестирование

### Python

Проверки разметки flash и отсутствия пересечения default motor/bus GPIO:

```sh
python -m unittest discover -s test/imu -p 'test_*.py'
```

### C++ host tests

| Каталог | Проверки |
| --- | --- |
| `test/imu` | ICM20948, ICM42688, ошибки fake bus, режимы/частоты, ESC beacon и DShot encoding |
| `test/i2c` | Address probe, кэширование ACK, сохранение диагностики рабочих ошибок |
| `test/barometer` | Барометрическая и навигационная логика |

Тесты используют stubs вместо аппаратных зависимостей. Для новых IMU/I2C/ESC
проверок использовался g++ в WSL с AddressSanitizer и UndefinedBehaviorSanitizer.
Пример запуска из корня репозитория в Linux/WSL:

```sh
g++ -std=c++17 -fsanitize=address,undefined \
  -I test/imu/stubs -I lib/Xsfc/src -I lib/AHRS/src \
  test/imu/test_icm42688.cpp -o /tmp/xsfc-test-icm42688
/tmp/xsfc-test-icm42688
```

Для I2C-теста дополнительно компилируется `Device/BusI2C.cpp`, для теста
кодирования DShot — `EscDriverBase.cpp`; выбираются соответствующие include paths.
Скрипт барометрических тестов: `bin/test_baro.ps1`.

Сборка прошивки, host regression tests и проверка реального оборудования —
разные уровни проверки. Их статус и незавершённые задачи отражаются в `TODO.md`.
